# Security and Privacy Baseline

Read this reference before implementing the feedback endpoint, media uploads, diagnostics, identity, or notifications.

## Establish the trust model

Decide who can submit before writing the route:

| Audience | Default protection |
|---|---|
| Signed-in staff or beta users | Require the existing session; derive identity and tenant server-side |
| Signed-in customers | Require the existing session; enforce tenant boundaries and per-user limits |
| Anonymous public visitors | Only when explicitly intended; durable IP/device throttling, bot protection, strict quotas, and operational monitoring are required |
| Native app | Verify the app's user token; App Check/attestation is defense in depth, not a substitute for authorization |

Do not quietly turn an internal debug widget into a public endpoint. A debug-only UI flag does not protect the server route.

For cookie-authenticated web routes, reuse the app's CSRF strategy. At minimum, reject unexpected `Origin`/`Host` combinations and do not enable broad CORS. Bearer-token native requests must validate the token and expected audience/issuer.

## Minimize and disclose data

Before submit, show a short, accurate summary such as:

> This report includes your description and page name. It also includes: screenshot, browser metadata. Review or remove attachments before sending.

Do not claim that a browser permission prompt explains downstream storage or tracker visibility; it does not. Disclose the chosen GitHub or Linear destination before sending.

Defaults:

- route/page name and app version: allowed;
- URL: strip query and fragment unless explicitly needed;
- screenshot, audio, video, files: added only by a user action and removable before submit;
- console, network, DOM/HTML, device identity, user identity: off;
- email notification: off and never persisted without an explicit "remember" choice.

Provide a masking convention such as `data-feedback-private` or `data-feedback-mask`. Element selection, screenshots generated by app code, and DOM diagnostics must exclude or obscure matching elements and their descendants. Never inspect password fields, payment fields, secrets, authentication screens, recovery codes, health data, or other known sensitive surfaces.

## Redact twice

Client-side redaction helps the reporter preview what will be sent. Repeat it on the server before storage or issue creation.

At minimum redact:

- `Authorization`, `Cookie`, `Set-Cookie`, API keys, bearer tokens, JWT-shaped values, private keys, and known secret environment names;
- query values for keys such as `token`, `code`, `key`, `secret`, `password`, `email`, and `session`;
- form values, input values, textarea contents, and contenteditable text from DOM snapshots;
- headers and request/response bodies from network diagnostics;
- excessive user text copied from selected DOM elements.

Use bounded, circular-safe serialization. Treat redaction as defense in depth: when data is not necessary, do not collect it.

## Validate requests before expensive work

Use the project's schema library when available. Reject unknown top-level keys unless compatibility requires a deliberate passthrough.

Choose limits that fit the host, and enforce them on both client and server. A reasonable starting policy is:

- title: 1–120 Unicode characters;
- description: 1–10,000 characters;
- selected text: 2,000 characters;
- captures: at most 8;
- attachments: at most 5;
- single attachment: at most 10 MiB decoded;
- combined decoded media: at most 25 MiB;
- diagnostics: bounded entry counts and byte size;
- body/content length: reject before JSON parsing when the runtime exposes it.

Base64 adds roughly one-third overhead. For larger recordings or constrained serverless routes, use a two-step upload: the authenticated backend authorizes a short-lived upload to a fixed object key and size/type policy, then the feedback route accepts only that stored object ID. Do not accept arbitrary URLs.

## Harden uploads

- Allowlist only file types needed by the chosen features.
- Do not accept SVG, HTML, JavaScript, or other active content by default.
- Treat client filenames and MIME types as untrusted. Detect or verify file signatures server-side where practical.
- Generate opaque object keys; keep the original sanitized filename only as display metadata.
- Prevent path traversal and filename collisions.
- Scan risky document types when the host already has a scanning service; otherwise omit them or explicitly accept the risk.
- Delete partially uploaded/orphaned objects after a failed submission.
- Define retention and deletion behavior before launch.

## Choose storage visibility explicitly

**Private reviewer access — recommended:** keep objects private and link the issue to an authenticated admin/reviewer route that checks authorization before streaming the object. This requires reviewers to have access to the host app, but avoids leaking captures through bearer URLs.

**Expiring signed link:** acceptable for temporary debugging when reviewers understand the link will expire. Store an object identifier in the issue, not a permanent secret-bearing URL, when the host can regenerate links.

**Public unlisted object:** only after explicit approval. Use high-entropy keys, disable directory listing, set restrictive content disposition/type, document that anyone with the URL can access it, and apply retention cleanup. A private GitHub issue does not make an external public object private.

Never call `makePublic()`, configure public container access, or widen storage rules simply because a provider is detected.

## Protect issue creation

- Provider, repository or Linear team/project/state, labels, and issue template are server configuration, never client input.
- Limit the GitHub App installation to the intended repository and grant only Issues read/write; for Linear, restrict API-key teams/permissions or OAuth scopes per [linear.md](linear.md).
- Normalize category through a server allowlist.
- Escape untrusted values used in markdown headings, tables, links, or HTML emails.
- Do not put email addresses, internal user IDs, access tokens, or raw diagnostics into public repositories.
- Use an idempotency key or stored submission record when a retry could create duplicate issues.
- Handle the selected provider's rate limits; do not retry without a stopping condition or retry an uncertain create as a new submission.

## Abuse controls

For any endpoint reachable outside a trusted internal session:

- use a durable rate limiter shared across instances;
- apply per-user and per-IP budgets, with tighter media quotas;
- use the host's bot challenge/attestation where available;
- record minimal security telemetry without logging report bodies or secrets;
- return `429` with a stable error code and retry guidance;
- cap concurrent/total storage consumption and alert on unusual volume.

In-memory maps are not sufficient on serverless or multi-instance deployments.

## Failure behavior

- Preserve the user's draft on retryable failures.
- Do not create an issue if required uploads failed; clean up unclaimed uploads or mark them for cleanup. Preserve attachments for reconciliation when issue creation succeeded or its outcome is uncertain.
- Do not expose provider messages, stack traces, bucket names, or credential state to the client.
- Use a request/submission ID in server logs and the generic client error response.
- If setup is incomplete, return `setup_required` without disclosing which secret value is absent to anonymous callers.

## Retention and deletion

State where feedback data lives and how long media/diagnostics are retained. Prefer automatic lifecycle deletion for media and diagnostics. If the product allows users to request deletion, retain a server-side mapping from submission ID to issue/object IDs without exposing that mapping in the client.
